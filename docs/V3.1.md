# V3.1 — module expérimental

Base : 7b3f692993a1f0c14303551c9c83f6a9c2880293. Module existant conservé, ajout de `vinted-adapter.js` et `vinted-ui.js`, sans modification de core.js, des bases produits ou des sauvegardes.

Le client demande explicitement un test sans publication. Cela ne prouve pas un accord de Vinted. Aucune autorisation officielle de cette intégration n’a été fournie. Les conditions officielles restent référencées dans README.

Le pont GM est vérifié par relecture et intégrité du format de sauvegarde V2. Un identifiant aléatoire dans le fragment du lien sélectionne le bon transfert ; aucune photo ni texte privé dans l’URL. Le module ne traite qu’un produit et expire logiquement après 24 h. L’effacement des données produits n’est jamais invoqué. Pas de serveur de photos, API privée, CAPTCHA, dissimulation, temporisation d’évitement ou publication.

La sélection automatique utilise des correspondances exactes et uniques. En cas d’absence/ambiguïté, le champ reste manuel. Les nouveaux attributs dépendant de la catégorie n’existent pas dans le modèle V1/V2 ; le module ne les invente pas. Les libellés de marque/état doivent correspondre à la langue de l’interface Vinted.

Les tests FileList utilisent réellement DataTransfer et l’affectation à input.files sur WebKit/Chromium. Ils comparent nombre, ordre et octets et observent les événements natifs. Ils ne valident ni les restrictions Orion/Violentmonkey iOS, ni le téléversement Vinted réel. Le pont GM est simulé par le contexte de test ; son fonctionnement sur l’extension réelle doit être essayé après installation.

Le verrou Web Locks évite deux tentatives simultanées par transfert sur la même origine. Le marqueur persistant est écrit avant le premier envoi des photos : une interruption entraîne une reprise sans photos, plutôt qu’un nouvel envoi silencieux. Il faut préparer un nouveau transfert pour recommencer les photos sur un formulaire vide. Aucun mécanisme ne crée une annonce ou ne clique sur Publier/Sauvegarder le brouillon.

Les statuts « À vérifier » indiquent une tentative, pas une validation serveur. Un sélecteur ayant reçu les fichiers n’est pas une preuve de téléversement accepté ; vérifier les miniatures natives et leur ordre. Aucun test réel d’envoi de fichiers ou d’événements par le userscript n’a été réalisé à cette étape.

Suite : 38 tests (22 tests de logique et 16 parcours mobiles). Les quatre scénarios nouveaux exécutés sur WebKit/Chromium ne remplacent pas un test dans l’extension réelle. La CI vérifie aussi que les métadonnées et le userscript générés correspondent aux sources.
